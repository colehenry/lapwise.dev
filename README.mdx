# lapwise.dev

A Formula 1 analytics platform I built because I got tired of bouncing between five different sites just to get a complete picture of a race weekend. It's live at [lapwise.dev](https://lapwise.dev).

The idea is simple: pull together race results, driver stats, telemetry, and historical data going back to 1950, and display it in a way that's actually useful to someone who follows the sport. Not just a table of standings, but lap-time progressions, tyre strategy timelines, qualifying sector comparisons, weather overlays — the kind of stuff that helps you understand _why_ a race played out the way it did.

---

## What it covers

- Race results and standings from 1950 to the current season
- Lap-by-lap telemetry (2018 onwards via FastF1)
- Driver and constructor profiles with full career history
- Qualifying breakdowns including sector times per segment (Q1/Q2/Q3)
- Sprint race and sprint qualifying support
- Tyre strategy and pit stop visualization
- Circuit stats and location info
- Upcoming race weekend schedule

## Running it locally

### Backend

Requires Python 3.11.14 exactly. The `.python-version` file enforces this.

```bash
cd backend
python3.11 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Copy `.env.example` to `.env` and fill in your database URL and API key:

```bash
DATABASE_URL=postgresql+asyncpg://user:pass@host/db?ssl=require
LAPWISE_API_KEY=your-key-here
CORS_ORIGINS=http://localhost:3000
```

Apply migrations and start the server:

```bash
alembic upgrade head
uvicorn app.main:app --reload
# API is now at http://localhost:8000
# Swagger docs at http://localhost:8000/docs
```

### Frontend

```bash
cd frontend
npm install
```

Create a `.env.local`:

```bash
NEXT_PUBLIC_API_URL=http://localhost:8000
NEXT_PUBLIC_API_KEY=your-key-here
```

```bash
npm run dev
# App is at http://localhost:3000
```

## Data ingestion

The dev database comes pre-loaded, so you only need to run ingestion if you're pulling in a new season or specific rounds.

```bash
cd backend
PYTHONPATH=$PWD python scripts/ingest_season.py 2024
```

The ingestion pipeline is split into modules under `scripts/ingest/`:

- `circuits.py` — track metadata
- `sessions.py` — session types (race, qualifying, sprint, sprint qualifying)
- `participants.py` — drivers and teams per season
- `results.py` — finishing positions, points, grid positions, qualifying times
- `telemetry.py` — lap-by-lap data, sector times, weather, track status
- `highlights.py` — YouTube video IDs for race highlights

Scripts are idempotent — running them multiple times won't create duplicate records. FastF1 caches session data locally under `cache/` (can get large, safe to delete).

Historical data before 2018 comes from Jolpica and has no telemetry. Post-2018 data uses FastF1's access to F1's live timing feed.

## API

All endpoints require an `X-API-Key` header. No auth needed for `/health`.

```bash
curl https://api.lapwise.dev/api/results/2024 \
  -H "X-API-Key: your-key"
```

### Endpoints


## Database schema

The database has nine tables. A few things worth knowing:

**Teams are year-partitioned.** The same constructor can have multiple records across years because names, colors, and ownership change (e.g., Racing Point became Aston Martin in 2021). Each year gets its own record.

**Sessions is a single table for all session types.** Race, qualifying, sprint race, and sprint qualifying all live in the `sessions` table differentiated by `session_type`.

**Lap data is the largest table.** Each session has ~1000 lap records with sector times, speed trap readings, tyre compound, stint number, pit in/out times, and a computed `pit_duration_seconds` column calculated directly by PostgreSQL.

**Headshots are stored per session result.** Not on the driver record itself — because a driver's photo, team kit, and number can change between seasons and teams.

## Architecture notes

The backend uses a services layer pattern to keep the routers thin. Routers handle HTTP — validation, status codes, error responses. Services handle database queries and business logic.

```python
# Router only handles HTTP
@router.get("/{driver_code}")
async def get_driver(code: str, db = Depends(get_db), _ = Depends(verify_api_key)):
    driver = await DriverService.get_driver_profile(db, code)
    if not driver:
        raise HTTPException(status_code=404, detail="Driver not found")
    return driver
```

The frontend uses React Query for all data fetching. It caches responses client-side so navigating back to a page that's already been visited doesn't hit the API again.

```typescript
const { data, isLoading } = useQuery({
  queryKey: ["driver", driverCode],
  queryFn: () =>
    fetch(`${API_URL}/api/drivers/${driverCode}`, {
      headers: { "X-API-Key": API_KEY },
    }).then((r) => r.json()),
  staleTime: 1000 * 60 * 60, // 1 hour
});
```

Styling uses semantic tokens defined in `globals.css` — things like `bg-bg-primary`, `text-text-secondary`, `border-border-primary`. This keeps the dark theme consistent without hardcoding hex values everywhere.
